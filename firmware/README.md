# Прошивка

Заготовка своего механизма поиска (шаг 1 из D-32) в `app/`: собирается под nRF54L15 DK, на железе не проверена. Поведение описано в [docs/concept.md](../docs/concept.md#режимы-работы), протокол рекламы и GATT — в [docs/protocol.md](../docs/protocol.md).

Прошивка своя, под MIT (D-32). Everytag (GPLv3) — только справочник: его код не копируется, форматы пакетов берутся из открытых описаний.

Порядок работ (D-32):

1. Свой механизм поиска на nRF54L15 DK: наборы рекламы Cricket Coded и Cricket 1M, режимы, драйверы, команда «пищи» из приложения.
2. Позже — наборы Apple Find My и Google Find Hub; координаты из сетей опрашивает приложение (D-33, [docs/app.md](../docs/app.md#краудсорсинговые-сети)).

План:

- Zephyr / nRF Connect SDK v3.4.2 (см. раздел «Версия SDK»), модуль Insight SiP ISP2454-LX (nRF54L15, 1,5 МБ RRAM, 256 КБ ОЗУ; D-29). Две цели сборки: своя плата `cricket_tag/nrf54l15/cpuapp` (описание в `boards/cricket/cricket_tag/`) и отладочная nRF54L15 DK `nrf54l15dk/nrf54l15/cpuapp`.
- Выводы модуля: карта в [hardware/cricket-tag/README.md](../hardware/cricket-tag/README.md#схема) (D-29). На NFC-выводах P1.02/P1.03 — I2C: на nRF54L их освобождает регистр NFCT.PADCONFIG (после сброса 1 — режим NFC), а Zephyr сбрасывает его только на nRF54H, поэтому это делает `board.c` платы. На P2 нет прерываний: CHRG_N читать опросом. Пищалка — PWM20 на P1.04; GRTC PWM (128 Гц) не годится.
- Свои наборы рекламы: Cricket Coded (Coded PHY S8, +8 dBm, подключаемый) и Cricket 1M для телефонов без Coded PHY.
- Наборы рекламы одновременно, через extended advertising: у каждого набора свой identity-адрес (`bt_id_create`, `CONFIG_BT_ID_MAX`, `CONFIG_BT_EXT_ADV_MAX_ADV_SET`), адрес Apple меняется через `bt_id_reset` при остановленном наборе. У Everytag одна реклама за раз и смена публичного адреса всего контроллера — так делать не нужно.
- Apple Find My (позже): формат OpenHaystack — шаблон рекламы 31 байт, адрес из первых 6 байт публичного ключа P-224 (старшие биты 11, статический случайный адрес), до N ключей со сменой по таймеру. Ключи генерирует приложение при привязке и записывает в маячок по своему GATT-сервису.
- Google Find Hub (позже): формат FHN с ключом, полученным приложением; сначала постоянный EID, сменный EID по спецификации FHN (AES, secp160r1, micro-ecc) — доработка, для неё нужны непрерывные часы (SHIP как System ON с GRTC).
- Режимы ON_DRONE, ESCALATE, ALARM, BEACON, STANDBY, LOW_BAT, SHIP.
- Признаки падения: MSP_STATUS (armed) по UART, удар по LIS2DH12, нарастание тревоги как запасной вариант.
- LIS2DH12 на I2C по адресу 0x19 (SA0 на VDD_IO), прерывание по удару на INT1 (ACC_INT1).
- Пищалка: ШИМ на BUZ_DIN, режим PAM8904E выводом BUZ_EN1 (0 — 1x, 1 — 3x; EN2 на VBAT, D-28). У CPT-1117-83 (D-27) громкость высокая широкой полосой 3–8 кГц: частоту или качание частоты подобрать замером.
- Без 5 В от полётника вывод UART_TX перевести во вход, чтобы не питать полётник через его защитные диоды, и выключить UART целиком: включённый приёмник UARTE держит HFCLK (сотни мкА), а UART_RX через 1 кОм висит на обесточенном полётнике.
- Режим 3x PAM8904E (BUZ_EN1 = 1) на полном аккумуляторе даёт размах до 25 В — ровно предел CPT-1117-83. Пока идёт заряд (VBAT до 4,24 В), использовать 1x или не пищать.
- Радио выключено, пока дрон armed: не мешать ELRS 2,4 ГГц.
- Чтение GPS с полётника по MSP, последние координаты в рекламе Cricket.
- Кнопка: выключение тревоги, привязка, режим хранения, загрузчик.
- Обновление прошивки по BLE (MCUboot + SMP) только в окне DFU: кнопка зажата 3 с с подачи питания (см. «Обновление прошивки»).
- Источник LFCLK: кварц 32,768 кГц внутри модуля (LFXO, нагрузочные ёмкости внутренние). Datasheet ISP2454 R7, разд. 2.5, рекомендует 19 пФ и предлагает дописать 19000 в binding `nordic,nrf54l-lfxo.yaml`. В SDK v3.4.2 этого мало: `soc/nordic/nrf54l/soc.c` проверяет `BUILD_ASSERT`, что значение не больше 18 000 фФ (предел внутренних конденсаторов nRF54L). Поэтому в плате стоит 18 пФ — ближайшее допустимое; уход частоты проверить на первых платах. HFXO 32 МГц: в datasheet значения нет, стоит 15 пФ, как у DK. DC/DC включён: токи в datasheet даны с ним.
- Сканирование в приложении на Pixel: режим PHY_LE_ALL_SUPPORTED, не только Coded. Подробности в [docs/app.md](../docs/app.md).

## Заготовка `app/`

Сборка (SDK v3.4.2, sysbuild, результат в `firmware/build/`, он в `.gitignore`):

```bash
firmware/build.sh
```

Аргументы: плата (по умолчанию `nrf54l15dk/nrf54l15/cpuapp`), аргументы `west build` и после `--` аргументы CMake, например `firmware/build.sh cricket_tag/nrf54l15/cpuapp -p always`. Скрипт передаёт `BOARD_ROOT=firmware`, чтобы находилась своя плата. Прошивка по SWD: `west flash -d firmware/build` внутри toolchain-окружения — sysbuild заливает и MCUboot, и подписанное приложение.

Проверено 2026-11-11: обе платы собираются с MCUboot без предупреждений в нашем коде. Предупреждения SDK: `Deprecated symbol NRF_PLATFORM_LUMOS` и `BOOT_MAX_IMG_SECTORS` из конфигурации MCUboot; без закрытого ключа — ещё об отладочном ключе подписи (см. «Обновление прошивки»). Объём — в разделе «Объём флеш-памяти»; DK с `msp-dk.overlay` тоже собирается.

### Плата `cricket_tag`

`boards/cricket/cricket_tag/` — описание платы по карте выводов из [README платы](../hardware/cricket-tag/README.md#схема):

| Узел | Выводы | Что в описании |
|---|---|---|
| MSP | UARTE30: TX P0.02, RX P0.00 | 115200; в состоянии sleep выводы отключены, чтобы не питать обесточенный полётник |
| LIS2DH12 | TWIM21: SDA P1.02, SCL P1.03; INT1 P1.11 | `st,lis2dh12` на 0x19, 400 кГц, подтяжки на плате |
| Пищалка | PWM20 канал 0 на P1.04; EN1 P2.05 | `buzzer-pwm`, `buz-en1-gpios` в `zephyr,user` |
| Вспышка | P2.02 (затвор 2N7002) | `flash-led`, `led0` |
| Кнопка | P1.05 на GND, подтяжка внутри | `user-button`, `sw0`, `mcuboot-button0` |
| VIN_SENSE | P0.03 | `vin-sense-gpios`: прерывание, пробуждение из System OFF |
| CHRG_N | P2.04, подтяжка внутри | `chrg-gpios`, опросом (на P2 нет прерываний) |
| VBAT | AIN3 (P1.07), делитель 1 МОм / 1 МОм | `io-channels`, усиление 1/4, выборка 40 мкс (максимум) из-за делителя 500 кОм с C3 100 нФ |

Лога по UART на плате нет: UARTE30 занят полётником. В отладочной сборке лог идёт по SWD через RTT (включается по умолчанию для этой платы в `app/Kconfig`); RTT держит ток высоким до передёргивания питания, ток мерить только в release-сборке (см. «Низкое потребление»).

На плате приложение берёт 5 В с VIN_SENSE (прерывание, после SHIP появление 5 В будит маячок), заряд — опросом CHRG_N с флагом в рекламе; пока идёт заряд, пищалка работает только в 1x. Долгое удержание кнопки при наличии 5 В в SHIP не переводит: 5 В разбудили бы маячок сразу.

| Файл | Что делает |
|---|---|
| `src/status.c` | состояние маячка и сборка 22 байт полезной нагрузки; ID — CRC32 от FICR DEVICEID |
| `src/adv.c` | наборы Cricket Coded (extended, Coded S8) и Cricket 1M (legacy, с именем в ответе на сканирование), оба подключаемые, +8 dBm через vendor-команду HCI; интервалы по режимам, перезапуск после соединения |
| `src/gatt.c` | сервис Cricket: состояние (read/notify), управление (FIND, SILENCE) |
| `src/buzzer.c` | ШИМ пищалки и вспышка светодиода по шаблонам; вывод EN1 PAM8904E (1x/3x) — если описан в `zephyr,user` |
| `src/battery.c` | VBAT через делитель (`zephyr,user`: `io-channels`, `vbat-full-ohms`, `vbat-output-ohms`); на DK не измеряется, LOW_BAT не срабатывает |
| `src/inputs.c` | кнопка: короткое, удержание 3 с, 8 с (решение по отпусканию); на DK кнопки 1–3 имитируют 5 В, armed и удар |
| `src/msp.c` | MSP v1 к полётнику по `msp-uart`: MSP_BOXIDS (какой бит флагов — ARM), MSP_STATUS каждые 250 мс, MSP_RAW_GPS каждую секунду; только при 5 В, без них UART приостановлен (`CONFIG_CRICKET_MSP`) |
| `src/impact.c` | удар по LIS2DH12 (`accel0`): «любое движение» на INT1 с фильтром высоких частот, порог `CONFIG_CRICKET_IMPACT_MG` (8 g); датчик работает только при 5 В, иначе приостановлен (`CONFIG_CRICKET_IMPACT`) |
| `src/dfu.c` | обновление по BLE: подтверждение нового образа для MCUboot при старте, фильтр команд SMP вне окна DFU |
| `src/wdog.c` | сторожевой таймер WDT31: 30 с, кормится тиком режимов, останавливается перед System OFF |
| `src/pair.c` | привязка телефона: окно привязки 60 с, отказ в привязке вне окна, ключи в разделе настроек (ZMS), команда FORGET ([protocol.md](../docs/protocol.md#привязка-и-защита)) |
| `src/modes.c` | режимы ON_DRONE…SHIP по [concept.md](../docs/concept.md#режимы-работы), всё в системной очереди работ |

Время режимов (`modes.c`): ESCALATE 45 с с тихим чириканьем раз в 5 с, затем ALARM; ALARM — серия писков раз в 5 с, через 45 мин BEACON; BEACON — писк раз в минуту; удар считается, если был за 10 с до пропажи 5 В; данные MSP считаются свежими 5 с (MSP повторяет состояние armed раз в секунду); при появлении 5 В прошлое состояние armed и удар забываются, до ответа MSP дрон считается disarmed; LOW_BAT ниже 3,4 В, SHIP ниже 3,2 В.

### MSP: настройка полётника

На полётнике UART, к которому припаян маячок, включить MSP на 115200: в Betaflight — вкладка Ports, колонка Configuration/MSP; в INAV — то же. Маячок спрашивает:

| Команда | Код | Что берёт |
|---|---|---|
| MSP_BOXIDS | 119 | номер бита ARM в флагах режимов (постоянный ID режима ARM — 0) |
| MSP_STATUS | 101 | флаги режимов (`uint32` со смещения 6) → armed |
| MSP_RAW_GPS | 106 | fix, число спутников, широта и долгота (1e-7°); координаты берутся при fix ≥ 2 и не меньше 4 спутников |

Без ответов MSP маячок полагается на удар и нарастание тревоги (ESCALATE). Формат проверен только по исходникам протокола, на полётнике — нет.

### Удар: порог

Порог 8 g по изменению ускорения (фильтр высоких частот убирает тяжесть), датчик 16 g, 400 Гц, режим low-power. Вибрации в полёте и жёсткая посадка не должны его превышать, удар при падении — должен; подобрать на дроне (`CONFIG_CRICKET_IMPACT_MG`). Не проверено: срабатывает ли событие «high» LIS2DH12 по модулю ускорения, то есть на удары в обе стороны по оси.

### Проверка на nRF54L15 DK

| Элемент DK | Роль |
|---|---|
| LED1 (P1.10, PWM20) | пищалка: светится в такт; пьезоизлучатель можно подключить к P1.10 |
| LED0 | вспышка |
| Button 0 | кнопка маячка |
| Button 1 | имитация 5 В: вкл/выкл |
| Button 2 | имитация armed по MSP: вкл/выкл |
| Button 3 | имитация удара |
| VCOM (UART) | лог, 115200 |

Сценарии: при включении — STANDBY. Button 1 → ON_DRONE; Button 2 → armed, реклама выключается; Button 1 → 5 В пропало → ALARM. Без Button 2 и Button 3 пропажа 5 В даёт ESCALATE, а через 45 с — ALARM. Короткое нажатие Button 0 гасит тревогу. Рекламу видно в nRF Connect for Mobile: Manufacturer data `0xFFFF`, на Pixel — сканирование 1M и Coded одновременно ([app.md](../docs/app.md)). Команда FIND — запись `01 0A` в характеристику управления (пищать 10 с). Вне тревоги телефон сначала надо привязать: удержать Button 0 3 с, затем записать команду — nRF Connect предложит привязку. В ESCALATE, ALARM и BEACON FIND (до 60 с) принимается и без привязки.

MSP можно проверить на DK с настоящим полётником до прихода плат: `msp-dk.overlay` включает UART30 (TX маячка P0.00 → RX полётника, RX маячка P0.01 ← TX полётника, общая земля). Сначала в Board Configurator поставить VDD DK 3,3 В (по умолчанию 1,8 В, а логика полётника 3,3 В). Сборка:

```bash
firmware/build.sh nrf54l15dk/nrf54l15/cpuapp -p always -- -DEXTRA_DTC_OVERLAY_FILE=msp-dk.overlay
```

5 В по-прежнему имитирует Button 1: MSP опрашивается только в ON_DRONE.

Не проверено на железе: работают ли два подключаемых набора на одном адресе одновременно (стек Zephyr это допускает, каждый набор занимает свой объект соединения, `CONFIG_BT_MAX_CONN=2`); фактическая мощность +8 dBm (лог `TX power` при старте); выход из System OFF по Button 0.

### Сторожевой таймер

WDT31 с таймаутом 30 с перезагружает маячок, если встала системная очередь работ: его кормит тик режимов, который идёт не реже раза в 10 с во всех режимах. Таймер считает и во сне, пауза только когда отладчик остановил процессор. Перед System OFF (SHIP) он останавливается — на nRF54L у WDT есть STOP, — иначе будил бы маячок из хранения. После сброса по сторожевому таймеру в логе предупреждение `previous reset by the watchdog`; маячок стартует в STANDBY или ON_DRONE, как при подключении аккумулятора.

### Низкое потребление

Что сделано для тока в покое:

- Радио, пищалка и вспышка работают по событиям; процессор просыпается на тик режимов раз в 10 с (в ESCALATE и ALARM — раз в секунду).
- UART к полётнику и LIS2DH12 приостановлены без 5 В (`msp.c`, `impact.c`).
- ШИМ пищалки при скважности 0 останавливает периферию (драйвер nRF PWM), PAM8904E выключен низким DIN и EN1.
- Кнопка, VIN_SENSE и INT1 акселерометра ждут фронта через механизм SENSE порта (`sense-edge-mask` в описании платы и в overlay DK), а не через каналы GPIOTE.
- LFCLK от кварца модуля, DC/DC включён (описание платы).
- **Release-сборка** без лога, консоли, RTT и баннера: `app/release.conf`.

```bash
firmware/build.sh cricket_tag/nrf54l15/cpuapp -p always -- -DEXTRA_CONF_FILE=release.conf
```

Как мерить: Power Profiler Kit II в режиме источника вместо аккумулятора на площадках J2 (3,7–4,0 В), провода полётника не подключены, SWD отсоединён; после прошивки снять и снова подать питание. На DK — разъём измерения тока P6 (Current measurement), тоже release-сборка. Сравнить с оценкой [concept.md](../docs/concept.md#энергобюджет-оценка-уточнить-замером): STANDBY ~20–26 мкА, ALARM без пищалки ~65–93 мкА, SHIP ~4–5 мкА (из них модуль 0,6 мкА, остальное утечки TP4054, делители и LDO).

Не проверено: ток не измерялся — ни DK, ни платы ещё нет.

### Обновление прошивки

MCUboot (sysbuild, `app/sysbuild.conf`) с двумя слотами и обменом: новый образ пишется во второй слот, при перезагрузке MCUboot меняет слоты и запускает его в пробном режиме. Прошивка подтверждает образ сама, если поднялись Bluetooth и режимы (`dfu.c`); если новый образ упадёт раньше, после сброса MCUboot вернёт старый.

По воздуху обновление идёт через MCUmgr SMP (сервис SMP Bluetooth, группы image и os, MTU 498). Команды SMP принимаются только в **окне DFU**: кнопку зажать при подаче питания (подключение аккумулятора, сброс или пробуждение из SHIP) и держать 3 с — два коротких писка, в рекламе флаг 6. Окно длится 5 мин и продлевается на минуту каждой принятой командой. Вне окна SMP отвечает «доступ запрещён». Кроме того, SMP работает только по шифрованному соединению, то есть с привязанного телефона. Окно DFU, открытое кнопкой при подаче питания, заодно открывает окно привязки, чтобы обновить можно было и с нового телефона; с уже привязанного телефона окно DFU открывает команда `0x03`.

Как обновить:

1. Собрать: `firmware/build.sh cricket_tag/nrf54l15/cpuapp`. Пакет для обновления — `firmware/build/dfu_application.zip` (подписанное приложение `firmware/build/app/zephyr/zephyr.signed.bin`).
2. Открыть окно DFU на маячке.
3. В приложении nRF Connect Device Manager (Android, iOS) выбрать маячок `Cricket`, Image → Upload, пакет `dfu_application.zip`, режим Test and Confirm. Или с компьютера: `mcumgr --conntype ble --connstring peer_name=Cricket image upload zephyr.signed.bin`, затем `image test <хэш>` и `reset`.

**Ключ подписи — свой, ed25519** (2026-11-11). Закрытый ключ лежит вне репозитория: `~/.cricket/keys/mcuboot-ed25519.pem` (права 600) на компьютере владельца; другой путь задаёт переменная `CRICKET_MCUBOOT_KEY`. `build.sh` передаёт его в `SB_CONFIG_BOOT_SIGNATURE_KEY_FILE`; если файла нет, сборка подписывается открытым отладочным ключом SDK и пишет об этом. Открытая часть — в репозитории, `keys/mcuboot-ed25519.pub.pem`: по ней видно, какому ключу доверяют маячки.

- Публичный ключ зашит в MCUboot. Маячок, прошитый с ним по SWD, принимает по воздуху только образы, подписанные этим закрытым ключом. Сменить ключ на выпущенном маячке можно только по SWD.
- **Потеря закрытого ключа** — обновление по воздуху для всех выпущенных маячков пропадает, останется только SWD. Нужна резервная копия вне компьютера (менеджер паролей или зашифрованный носитель).
- Утечка ключа — любой сможет сделать образ, который маячок примет в окне DFU.
- Проверка образа: `imgtool.py verify -k ~/.cricket/keys/mcuboot-ed25519.pem firmware/build/app/zephyr/zephyr.signed.bin` (внутри toolchain, скрипт в `bootloader/mcuboot/scripts/` SDK). Проверено 2026-11-11: образ проходит с нашим ключом и не проходит с ключом SDK, в `autogen-pubkey.c` MCUboot — наш открытый ключ.

## Версия SDK

Прошивка ведётся на nRF Connect SDK **v3.4.2** (D-32), последнем выпуске на 2026-11-11. Раньше выбирался v2.8.0 только потому, что Everytag не собирается на 3.x (D-18); своя прошивка от этого не зависит. v2.8.0 остаётся установленным, но не используется.

```bash
nrfutil sdk-manager toolchain launch --ncs-version v3.4.2 -- west build -b nrf54l15dk/nrf54l15/cpuapp --sysbuild firmware/app -d firmware/build
```

Примеры кода для Bluetooth из интернета часто написаны под старый API: в 3.x, например, `BT_LE_ADV_OPT_CONNECTABLE` заменён на `BT_LE_ADV_OPT_CONN`, а `bt_hci_cmd_create` на `bt_hci_cmd_alloc`.

## Everytag как справочник

Что полезно посмотреть в [Everytag](https://github.com/vasimv/Everytag), не копируя код:

- после работы через J-Link RTT nRF держит ток в миллиамперах до снятия питания, программный сброс не помогает — замерять ток только после передёргивания питания;
- overlay для nRF54L15 DK включает `wdt31` и канал АЦП на VDD;
- настройки и ключи — в отдельном разделе NVS, переживают OTA; при первой прошивке стирать флеш целиком;
- приём настроек по BLE короткими окнами (2 с в минуту), чтобы не тратить ток на подключаемую рекламу.
